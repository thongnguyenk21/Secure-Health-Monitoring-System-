# Locked Decisions

| # | Date | Decision | Rationale |
|---|---|---|---|
| D1 | 2026-10-09 | Rust (Cargo workspace) for ESP32-C3 firmware, all edge services, cloud backend (axum + sqlx). Drop Spring Boot/Flyway. | User wants to learn Rust; shared types, lightweight for Pi |
| D2 | 2026-10-09 | Python only for ML: PyTorch, SSL, Flower client/server, benchmarks, experiments (uv) | No practical Rust option for training/Flower |
| D3 | 2026-10-09 | Mobile keeps React Native (TypeScript) | User chose to keep the familiar stack |
| D4 | 2026-10-09 | `shared/protocols` (Protobuf + OpenAPI + JSON Schema) is the cross-language contract | Multiple languages need a single source of truth |
| D5 | 2026-10-09 | Develop on Linux x86_64 (Docker + K3s) first, then move to Raspberry Pi 3B+ (1GB RAM, aarch64) | Real-world deployment target |
| D12 | 2026-10-09 | Code documentation standard: every public item gets a brief summary plus param/return/error sections in the language's native format (rustdoc, Google-style docstrings, TSDoc); enforced in CI. Spec: docs/engineering/CODING_CONVENTIONS.md | User request |
| D21 | 2026-10-12 | Wearable offline mode (option A): the ESP32 always writes every sample into an on-device ring buffer first; while the BLE link to the Pi is up the buffer is drained continuously (near empty), while out of range it accumulates and overwrites the OLDEST entries when full (dropped counter kept); on reconnect the backlog is sent oldest-first and records are removed only after the Pi acknowledges their sequence number (at-least-once; the Pi/cloud de-duplicate by idempotency key). Timestamps use the device monotonic clock plus a time anchor given at reconnect. Phone-as-gateway (option B) is LATER. | User choice 2026-10-12: device must keep working when worn outside Pi range |
| D22 | 2026-10-14 | Wearable firmware is written in C on ESP-IDF (FreeRTOS, NimBLE). One C++ file (`model_runner.cpp`) wraps TensorFlow Lite Micro (`espressif/esp-tflite-micro`, ESP-NN) and exposes `extern "C"` functions. Supersedes D1 (firmware part) and D16. The Rust crates `iomt-frames`, `offline-buffer` and `snn-lif` become reference implementations; the C port keeps the 16-byte record and ack semantics bit-for-bit, so Pi and cloud are unchanged. | The requirement (`docs/specs/JD.md` §3.1) asks for TFLM on the device; TFLM is C++ with no official C API |
| D23 | 2026-10-14 | On-device activity classifier is an SNN: LIF neurons trained offline with surrogate gradients (snnTorch), unrolled over T time steps into a static graph, quantised to int8 and run by TFLM (< 5 ms). Fallback if the spike step cannot be expressed with TFLM ops at acceptable accuracy: a hand-written LIF core in C, with TFLM running the non-spiking layers. Spike-check is a ≤ 3-day item in the M0.5 week. | Satisfies both "SNNs on the MCU" and "TFLM inference" in the requirement |
| D24 | 2026-10-14 | No MVP / LATER split for the product scope: federated learning (`edge-train/local-trainer`, `cloud/fl-server`), firmware OTA over BLE (A/B partitions, Ed25519-signed images) and device hardening (ESP32-C3 Secure Boot v2 + flash encryption) are in scope. Still out of scope: clinical trials and certification, phone-as-gateway. | Production-grade target chosen by the user |
| D25 | 2026-10-14 | No Prometheus, Alertmanager or node_exporter. Services expose `/healthz` and `/readyz` and log JSON to stdout. Grafana is used only during evaluation to show measured stability evidence; it is not deployed with the system. Edge-lite RAM budget becomes 240 MB (no node_exporter). | Smaller system; Grafana is only needed for evidence |
| D26 | 2026-10-14 | Roles are patient, clinician and admin only (the researcher role is dropped; the admin publishes models and runs federated rounds). A web app (React + TypeScript, same OpenAPI client as mobile) serves clinicians and admins; mobile (React Native) serves patients and clinicians. | Fewer roles, simpler RBAC; clinicians need a large-screen view |
| D27 | 2026-10-14 | The on-device SNN becomes multi-task: a shared LIF hidden layer (~48 neurons) feeds two LIF heads, activity (rest/walk/run/unknown) and health screening (normal, tachycardia at rest, bradycardia, SpO2 drop, suspected fall). Inputs per second: 12 accelerometer features plus HR, SpO2, step cadence and signal quality. Step cadence and walking speed are computed by formula, not by the SNN. The record's `activity` byte is split into two 4-bit fields (activity, health), which is a `firmware.v1` contract change and needs a version bump before firmware ships. Output is screening for early alerts, not a medical diagnosis; the Pi model and cloud rules remain the final arbiters. | Activity context removes false alarms (HR 140 is normal while running, abnormal at rest); the requirement asks the IoT-tier SNN to improve detection of medical incidents (`docs/specs/JD.md` §4 phase 2) |
| D28 | 2026-10-15 | Clients split by role: the mobile app (React Native) is for patients only (home with context-aware health status, full-screen fall/emergency alert with countdown, history with alert timeline, device pairing, OTA status and consent); the web app (React) is for clinicians (patient list sorted by priority, patient detail, alert acknowledge and notes) and admins (devices, users and roles, OTA releases, federated learning rounds, audit log, service health). Amends D26, which let clinicians use the mobile app too. | Clinicians work at a desk and need a large-screen triage view; the patient app stays simple |
