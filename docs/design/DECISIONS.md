| D5 | 2026-10-09 | Develop on Linux x86_64 (Docker + K3s) first, then move to Raspberry Pi 3B+ (1GB RAM, aarch64) | Real-world deployment target |
| D12 | 2026-10-09 | Code documentation standard: every public item gets a brief summary plus param/return/error sections in the language's native format (rustdoc, Google-style docstrings, TSDoc); enforced in CI. Spec: docs/engineering/CODING_CONVENTIONS.md | User request |
| D21 | 2026-10-12 | Wearable offline mode (option A): the ESP32 always writes every sample into an on-device ring buffer first; while the BLE link to the Pi is up the buffer is drained continuously (near empty), while out of range it accumulates and overwrites the OLDEST entries when full (dropped counter kept); on reconnect the backlog is sent oldest-first and records are removed only after the Pi acknowledges their sequence number (at-least-once; the Pi/cloud de-duplicate by idempotency key). Timestamps use the device monotonic clock plus a time anchor given at reconnect. Phone-as-gateway (option B) is LATER. | User choice 2026-10-12: device must keep working when worn outside Pi range |
| D22 | 2026-10-14 | Wearable firmware is written in C on ESP-IDF (FreeRTOS, NimBLE). One C++ file (`model_runner.cpp`) wraps TensorFlow Lite Micro (`espressif/esp-tflite-micro`, ESP-NN) and exposes `extern "C"` functions. Supersedes D1 (firmware part) and D16. The Rust crates `iomt-frames`, `offline-buffer` and `snn-lif` become reference implementations; the C port keeps the 16-byte record and ack semantics bit-for-bit, so Pi and cloud are unchanged. | The requirement (`docs/specs/JD.md` §3.1) asks for TFLM on the device; TFLM is C++ with no official C API |
| D23 | 2026-10-14 | On-device activity classifier is an SNN: LIF neurons trained offline with surrogate gradients (snnTorch), unrolled over T time steps into a static graph, quantised to int8 and run by TFLM (< 5 ms). Fallback if the spike step cannot be expressed with TFLM ops at acceptable accuracy: a hand-written LIF core in C, with TFLM running the non-spiking layers. Spike-check is a ≤ 3-day item in the M0.5 week. | Satisfies both "SNNs on the MCU" and "TFLM inference" in the requirement |
| D24 | 2026-10-14 | No MVP / LATER split for the product scope: federated learning (`edge-train/local-trainer`, `cloud/fl-server`), firmware OTA over BLE (A/B partitions, Ed25519-signed images) and device hardening (ESP32-C3 Secure Boot v2 + flash encryption) are in scope. Still out of scope: clinical trials and certification, phone-as-gateway. | Production-grade target chosen by the user |
| D25 | 2026-10-14 | No Prometheus, Alertmanager or node_exporter. Services expose `/healthz` and `/readyz` and log JSON to stdout. Grafana is used only during evaluation to show measured stability evidence; it is not deployed with the system. Edge-lite RAM budget becomes 240 MB (no node_exporter). | Smaller system; Grafana is only needed for evidence |
| D26 | 2026-10-14 | Roles are patient, clinician and admin only (the researcher role is dropped; the admin publishes models and runs federated rounds). A web app (React + TypeScript, same OpenAPI client as mobile) serves clinicians and admins; mobile (React Native) serves patients and clinicians. | Fewer roles, simpler RBAC; clinicians need a large-screen view |
| D27 | 2026-10-14 | The on-device SNN becomes multi-task: a shared LIF hidden layer (~48 neurons) feeds two LIF heads, activity (rest/walk/run/unknown) and health screening (normal, tachycardia at rest, bradycardia, SpO2 drop, suspected fall). Inputs per second: 12 accelerometer features plus HR, SpO2, step cadence and signal quality. Step cadence and walking speed are computed by formula, not by the SNN. The record's `activity` byte is split into two 4-bit fields (activity, health), which is a `firmware.v1` contract change and needs a version bump before firmware ships. Output is screening for early alerts, not a medical diagnosis; the Pi model and cloud rules remain the final arbiters. | Activity context removes false alarms (HR 140 is normal while running, abnormal at rest); the requirement asks the IoT-tier SNN to improve detection of medical incidents (`docs/specs/JD.md` §4 phase 2) |
| D28 | 2026-10-15 | Clients split by role: the mobile app (React Native) is for patients only (home with context-aware health status, full-screen fall/emergency alert with countdown, history with alert timeline, device pairing, OTA status and consent); the web app (React) is for clinicians (patient list sorted by priority, patient detail, alert acknowledge and notes) and admins (devices, users and roles, OTA releases, federated learning rounds, audit log, service health). Amends D26, which let clinicians use the mobile app too. | Clinicians work at a desk and need a large-screen triage view; the patient app stays simple |
| D29 | 2026-10-15 | Learning is split by tier. The wearable never trains or edits the signed model; it only keeps bounded per-user calibration in NVS, outside the OTA image: resting heart rate by EWMA (updated only at rest with signal quality ≥ 50), a resting-tachycardia threshold clamp(HR_rest + Δ, θ_min, θ_max) with clinician-set bounds, and a step-length factor from a walk of known distance. Real training stays on the edge training machine (local-trainer) and aggregation on the cloud FL server, which remains the only source of signed models. Patient feedback ("Tôi ổn" → false alarm) and clinician acknowledgement (→ true alarm) become labels; on those events the wearable sends the window's feature vector to the Pi in a separate BLE message (record format unchanged, `firmware.v1` minor bump), and the Pi passes it to local-trainer. Raw data and labels never leave the home. | Personalises alerts without breaking model signing, fits the ESP32-C3 (no FPU, ~400 KB RAM, TFLM is inference-only), and closes the gap that the edge had no SNN inputs to retrain on |
| D30 | 2026-10-15 | Network links and their stacks are fixed per link: (1) wearable ↔ Pi over BLE 5 GATT with LE Secure Connections and bonding, no IP; (2) Pi ↔ edge training machine over the home LAN with gRPC on TLS 1.3 mTLS, carrying feature vectors and labels (D29); (3) Pi → cloud gRPC (HTTP/2) on TLS 1.3 mTLS, port 9443; (4) local-trainer ↔ FL server with Flower's gRPC on TLS 1.3 mTLS; (5) cloud ↔ mobile and web REST/HTTPS through Caddy on 443, plus a WebSocket on the same origin for live alerts on the clinician web app; (6) cloud → phone through FCM HTTP v1, carrying only alert id and severity. All other cloud ports are closed. | One documented stack per link for the report's network view; the web app needs push-style alert delivery without polling |
| D31 | 2026-10-15 | The edge gateway becomes a Raspberry Pi 4 Model B with 4 GB RAM, and local-trainer (Flower client, PyTorch) runs on it as a fourth container; the separate edge training machine is dropped. The real-time services keep their 240 MB budget and priority. local-trainer is capped at 1.5 GB RAM and 2 of 4 CPU cores, runs at low priority and only when load is low (for example at night), and is paused if alert latency rises. Supersedes the edge-lite / edge-train machine split of ADR-0007 and the Pi 3B+ target; the Pi ↔ training-machine LAN link in D30 is no longer needed (feature vectors and labels stay inside the Pi). | The requirement places local training on the edge gateway (`docs/specs/JD.md` §3.2); a Pi 4 has the RAM and CPU for training the small SNN and edge models, and one device per home is simpler and cheaper than two |
| D32 | 2026-10-15 | The patient's phone becomes the outdoor gateway (supersedes the "phone-as-gateway" exclusion in D24; adds two links to D30). At home the wearable keeps sending to the Pi; out of the Pi's range it bonds over BLE 5 GATT + LESC with the mobile app, which runs the same link session as the Pi (handshake with time anchor and `boot_id`, CRC check, dedupe, `LinkAck`) and uploads summary records and alerts to the cloud over REST/HTTPS (JWT of the patient, the paired device bound to that account). Data is held in three layers so that no connection state loses records: the wearable ring buffer (900 records, about 15 min) when neither gateway is reachable; a durable queue on the gateway (SQLite in `edge-sync` on the Pi, local storage in the app) when the gateway has no network; the cloud, which deduplicates on `RecordKey (device_id, window_start, seq, boot_id)` when both paths deliver the same record. A gateway acks only after it has stored the records durably, the same rule for the Pi and the phone. Training follows option 1: the cloud sends the summary records a patient produced outdoors back to that patient's Pi, where local-trainer uses them with the home data; feature vectors and labels taken outdoors (D29) never go through the cloud: the app keeps them and hands them to the Pi over the home LAN. A new consent scope `model_training` is required before any record is used for training (Decree 13/2023/ND-CP treats health data as sensitive). Android first; iOS background BLE is a known limitation. Needs a contracts version bump (app uplink route, `model_training` consent, cloud → Pi download of outdoor summaries). Effort: +2–4 person-weeks (33–49 in total). | Falls and abnormal heart rates happen outdoors, where the old design could not alert anyone until the patient came home and lost data after 15 min. Routing summaries through the cloud adds no exposure (the cloud already stores them, D18), and keeping feature vectors and labels off the cloud preserves the federated-learning premise |
| D33 | 2026-10-15 | Deployment scope is one real wearable, one Raspberry Pi 4 and one cloud VPS. Scale and load targets are tested with simulated devices (`device-sim`, 30 devices for the API p95 test). Federated learning runs with the one real Pi plus simulated Flower clients. The design keeps its capacity for 5–30 wearables per deployment and 7–10 BLE links per Pi; only the built and measured setup shrinks. The S5 "5-node soak" becomes a 24-hour continuous run of the single wearable. | Owner decision for the capstone scope: one device is enough to show the full flow, and simulation covers scale |
| D34 | 2026-10-15 | The mobile app targets Android only; iOS support is dropped from scope and from future work. Amends D32 ("Android first; iOS background BLE is a known limitation") and the "React Native, Android and iOS" wording of D3. | Owner decision: the phone gateway needs a long-running background BLE session, which Android allows with a foreground service; one platform keeps the capstone scope small |
